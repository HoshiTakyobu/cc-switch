# CC Switch v3.20.3-unified.1

这是基于上游 CC Switch v3.20.3 的 fork 专用版本，目标是让 Codex 的官方托管账号与第三方中转站共享同一个 `custom` model provider、同一套故障切换队列和同一个会话历史视图。

## 实现的功能

### 1. 统一 model provider

- 由 CC Switch 管理的 OpenAI / ChatGPT OAuth 账号在接管时写入 `model_provider = "custom"`。
- 官方托管账号与中转站都通过 `[model_providers.custom]` 访问 CC Switch 本地代理。
- OAuth access token 不写入 Codex 的 `auth.json` 占位配置；代理会按当前选中的托管账号逐请求取令牌。
- 启动恢复会识别旧版遗留的 `cc-switch-official` 接管配置，并重建为 `custom`。

### 2. 官方托管账号加入故障切换

- 已绑定到 CC Switch Auth Center 的官方账号可以和中转站一起加入 Codex 故障切换队列。
- 队列仍严格遵循 CC Switch 的启用状态与顺序。
- 官方托管账号的可重试错误可以切换到下一个队列项。
- 未绑定、依赖 Codex 进程自身 OAuth 请求头的原生官方卡片不会被加入故障切换。这是安全边界：其调用方令牌无法在切换到其他账号时可靠替换。

### 3. 旧会话迁移到 `custom`

迁移同时覆盖两类旧 provider：

- Codex 内建官方桶 `openai`
- 旧版 CC Switch 接管桶 `cc-switch-official`

迁移会同时修改：

- `sessions` / `archived_sessions` 中 JSONL 的 `session_meta.model_provider`
- Codex `state_*.sqlite` 中 `threads.model_provider`

每个被修改的 JSONL 和 SQLite 数据库都会先备份到：

```text
~/.cc-switch/backups/codex-official-history-unify-v1/
```

迁移只改已识别的 provider id，不碰未知 provider、消息正文或其他会话字段。

## 正在使用的会话如何保证安全

本版本不会在 Codex 仍运行时修改会话文件或 state 数据库。

1. 检测到任何会拥有 session 的 Codex 主进程时，整批迁移延期，JSONL 和 SQLite 均保持原状。
2. CC Switch 每 15 秒重试一次。
3. 延期期间，顶层 provider 仍为 `custom`；配置中临时保留一个不活动的 `cc-switch-official` 本地代理兼容别名，只用于按 ID 恢复旧会话，不会用于创建新会话。
4. 所有 Codex 窗口和 CLI 进程退出后，CC Switch 才执行带备份的原子迁移。
5. 迁移完成标记会记录当前 Codex 目录以及 `openai`、`cc-switch-official` 两个来源桶；后续投影会清理不再需要的兼容别名。

因此，启用新版本时可以保留当前对话继续工作。要让当前对话和另一个旧会话最终都出现在 `custom` 历史中，请在工作结束后关闭所有 Codex 窗口/CLI，保持 CC Switch 运行至少 15 秒，再重新打开 Codex。

Codex 官方支持按 session/thread ID 恢复；兼容别名覆盖了“旧元数据尚未迁移”的过渡窗口。

## 安装说明

Release 提供 Windows x64 便携 EXE。该文件未签名，请手动退出旧版 CC Switch 后运行新文件；不会自动覆盖你当前安装的 `G:\CC Switch\cc-switch.exe`。
